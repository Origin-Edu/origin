The $2M Mistake

A Real OR Origin Story

North Atlantic, 1941

German U-boats were sinking Allied merchant ships faster than shipyards could replace them.

The Admiralty asked: Should convoys be large or small?

  • Large convoys: fewer targets, but slower to assemble and harder to maneuver
  • Small convoys: faster turnaround, but more targets spread across the ocean
  • Naval tradition favored small convoys — "don't put all eggs in one basket"

The Operational Research Team

Patrick Blackett (future Nobel physicist) assembled mathematicians, physicists, and statisticians.

They didn't guess. They structured the problem:

  • Decision: convoy size (number of merchant ships per escort group)
  • Objective: minimize ships lost per ton of cargo delivered
  • Constraints: escort vessels available, port capacity, assembly time
  • Uncertainty: U-boat positions, weather, mechanical breakdowns

The Answer: Large Convoys

The model showed detection probability grows sub-linearly with convoy size, while escort efficiency grows linearly.

Result: 50% reduction in shipping losses. Millions of tons saved.

Operational Research was born — not from better intuition, but from better structure.

The Central Question

How do we decide which truck takes which orders, from which depot, in what sequence — every single day — without guessing?

12 trucks × 3 depots × 200 orders = billions of possible assignments.

The dispatcher has 30 minutes each morning before trucks roll.

The Beginner's Confusion

"Is This Just Optimization?"

Optimization (the solver)

  • Finds the best values for decision variables
  • Given a fixed mathematical model
  • Output: "Set x₁=3, x₂=7, cost=$2,840"
  • ⚠ Blind to whether the model matches reality

Operational Research (the cycle)

  • 1. Problem Structuring — What are we really deciding?
  • 2. Modeling — Translate to math (variables, constraints, objective)
  • 3. Solving — Run the optimizer
  • 4. Validating — Does the solution work in practice?
  • 5. Implementing — Build the tool the dispatcher uses
  • 6. Monitoring — Track KPIs, detect drift, re-model

OR = the full lifecycle. Optimization is step 3. Steps 1, 2, 4, 5, 6 are where most value lives — and where most failures happen.

The Core Insight

Structure Beats Intuition

What the Dispatcher Game Reveals

Intuition (Human)

  • Fast on tiny problems (3 orders, 1 truck)
  • Collapses under combinatorial explosion
  • Biased by recent experience, not global view
  • Cannot quantify "how far from optimal"
  • No audit trail — "I just knew"

Structure (OR Model)

  • Scales: same logic for 10 or 10,000 orders
  • Exhaustive (or provably near-optimal)
  • Objective: every decision traced to cost function
  • Quantifiable gap: "We're 3.2% above optimum"
  • Reproducible: same input → same output

Good decisions come from good structure, not just smart people.

OR provides that structure systematically.

From Chaos to Model: The QuickShip Whiteboard

Three questions structure any OR model:

What do we decide?

Decision Variables

Which truck takes which order from which depot?

Objective Function

Minimize total cost: fuel + driver time + late penalties

Constraints

Pillar 1: Decision Variables — What We Control

For QuickShip, the core decision is assignment:


x_{ijk} = 
\begin{cases}
1 & \text{if truck } k \text{ takes order } j \text{ from depot } i \\
0 & \text{otherwise}
\end{cases}
  • Indices: i ∈ {N, C, S} depots, j ∈ {1..50} orders, k ∈ {1..12} trucks
  • Type: Binary (0/1) — a truck either takes an order or it doesn't
  • Count: 3 × 50 × 12 = 1,800 variables

Naming convention: x for binary assignment, y for continuous flow, z for auxiliary/logical.

Pillar 2: Objective Function — What We Want

QuickShip's total daily cost:


\min \sum_{i} \sum_{j} \sum_{k} 
\underbrace{c_{ijk}^{\text{fuel}}}_{\text{fuel cost}} 
+ \underbrace{c_{ijk}^{\text{time}}}_{\text{driver time}} 
+ \underbrace{c_{ijk}^{\text{late}}}_{\text{late penalty}} 
\; x_{ijk}
  • Single objective: Everything converts to dollars
  • Coefficients come from data: GPS traces → fuel, HR records → driver cost, customer contracts → penalty rates
  • Multi-objective alternative: Minimize cost and maximize on-time % → requires weighting or Pareto frontier

For Chapter 2: we stick to single-objective minimization. The structure is linear — each variable contributes independently.

Pillar 3: Constraints — What Limits Us

Five constraint families for QuickShip:

1. Each order assigned once


\sum_{i} \sum_{k} x_{ijk} = 1 \quad \forall j

2. Truck capacity


\sum_{i} \sum_{j} w_j x_{ijk} \le Q_k \quad \forall k

3. Time windows


a_j \le t_{ijk} \le b_j \quad \forall i,j,k \text{ with } x_{ijk}=1

4. Shift limits


\sum_{i} \sum_{j} \tau_{ijk} x_{ijk} \le T_k^{\max} \quad \forall k

5. Depot assignment (truck starts at one depot)


\sum_{j} x_{ijk} \le M \cdot y_{ik} \quad \forall i,k \quad \text{where } y_{ik} \in \{0,1\}, \sum_i y_{ik} = 1

The Complete LP Formulation


\min_{x,y} \quad \sum_{i,j,k} c_{ijk} x_{ijk}

\text{s.t.} \quad 
\sum_{i,k} x_{ijk} = 1 & \quad \forall j \in \text{Orders} \quad \text{(assignment)} \\
\sum_{i,j} w_j x_{ijk} \le Q_k & \quad \forall k \in \text{Trucks} \quad \text{(capacity)} \\
\sum_{i,j} \tau_{ijk} x_{ijk} \le T_k^{\max} & \quad \forall k \in \text{Trucks} \quad \text{(shift)} \\
\sum_{j} x_{ijk} \le M y_{ik} & \quad \forall i,k \quad \text{(depot link)} \\
\sum_{i} y_{ik} = 1 & \quad \forall k \quad \text{(single depot)} \\
x_{ijk} \in \{0,1\}, \; y_{ik} \in \{0,1\} & \quad \forall i,j,k

In matrix form: min c'x s.t. Ax ≤ b, x ∈ {0,1}n

  • c = cost coefficients (1,800 elements)
  • A = constraint matrix (~74 rows × 1,800 cols)
  • b = right-hand sides (capacities, shift hours, 1's)
  • x = our 1,800 binary decisions

  • Each constraint = a half-plane (line + one side)
  • Intersection = feasible region (convex polygon)

Modeling Choices That Change Everything

Same QuickShip problem, three critical forks:

Discrete vs. Continuous Time

  • Discrete: 15-min slots → MILP, exact but large
  • Continuous: t ∈ ℝ → NLP, smaller but non-convex
  • QuickShip uses discrete 15-min buckets — matches driver schedules

Aggregated vs. Detailed Routes

  • Aggregated: depot→zone cost matrix → fast solve
  • Detailed: street-level routing → TSP subproblems
  • QuickShip: aggregated for planning, detailed for execution

Hard vs. Soft Constraints

  • Hard: shift limit = 8 hrs (labor law)
  • Soft: time window + $50/hr penalty
  • QuickShip: hard on shifts, soft on windows

Each choice trades model fidelity against solve time. No free lunch.

Data: The Silent Partner

Where QuickShip's numbers actually come from:

Cost Coefficients (c)

  • Fuel: GPS traces + fuel card records → $/km per truck
  • Driver time: HR/payroll → $/hr loaded vs. empty
  • Late penalty: Customer contracts → tiered $/min

Constraint RHS (b)

  • Capacity: Vehicle specs (not "what we usually load")
  • Shift limits: Union agreement + safety regulations
  • Time windows: Customer promises (not wishes)

Garbage in, garbage out — but how to check?

  • Range checks: fuel cost ∈ [$0.50, $2.00]/km?
  • Cross-validation: GPS distance ≈ routing engine distance?
  • Sensitivity: if fuel cost ±10%, does assignment change?
  • Shadow prices: which constraints bind? (next chapter)

Inside the Black Box: Simplex in 3 Minutes

Linear programs live in a polyhedron — the feasible region defined by your constraints.

The Geometric Walk

  1. Start at a vertex (basic feasible solution)
  2. Check neighbors — adjacent vertices connected by an edge
  3. Pivot — move to a neighbor that improves the objective
  4. Stop when no neighbor is better → optimal

Key insight: The optimum of an LP is always at a vertex. Simplex just walks the edges.

QuickShip's LP relaxation (ignoring integrality) has ~50,000 variables. Simplex visits ~200 vertices. Not exhaustive — intelligent.

When Variables Must Be Integers: Branch & Bound

QuickShip's xijk are binary. LP relaxation gives fractional trucks — not implementable.

The Branch & Bound Algorithm

  1. Relax — solve LP with 0 ≤ x ≤ 1. Get fractional solution, objective = $12,450 (lower bound)
  2. Branch — pick a fractional variable (e.g., x0,5,2 = 0.6). Create two subproblems:
    • Node A: x0,5,2 = 0
    • Node B: x0,5,2 = 1
  3. Bound — solve LP at each node. If objective ≥ best integer solution found → prune
  4. Repeat until all nodes pruned or solved → proven optimal

The Model Missed: Stochasticity. Travel times aren't constants — they're distributions. Our MILP optimized for the average case, not the real case.

Deterministic OR assumes certainty. The world doesn't.

Stochastic OR: Two-Stage Programming

When data has variance, we optimize decisions before uncertainty resolves and recourse after.

Two-Stage Stochastic Program

First Stage (Here-and-Now)

Decide truck assignments & depot allocation before traffic is known.

min ∑ₖ cₖ xₖ + 𝔼[Q(x, ξ)]

xₖ = 1 if truck k used

Second Stage (Wait-and-See)

After traffic ξ realized: re-route, delay, or drop orders at penalty cost.

Q(x, ξ) = min ∑ qᵢ yᵢ(ξ)

s.t. A y(ξ) ≥ b(ξ) - T x

yᵢ = recourse actions (overtime, penalties)

Sample Average Approximation (SAA): Draw N scenarios ξ¹...ξᴺ from travel-time distributions. Solve deterministic equivalent:

min ∑ₖ cₖ xₖ + (1/N) ∑ₙ Q(x, ξⁿ)

As N → ∞, SAA solution → true stochastic optimum.

Implementation: From Dashboard to Dispatch

An optimal solution that never reaches the driver is worth $0.

Technical Pipeline

  1. Dashboard → REST API (JSON: routes, ETAs, load plans)
  2. API → TMS (Transportation Management System)
  3. TMS → Driver App (turn-by-turn, time windows, proof-of-delivery)
  4. App → Telemetry (GPS, scan timestamps, exceptions)

Feedback Loop

  1. Collect actuals vs. plan daily
  2. Recalibrate: travel-time distributions, service times, penalty rates
  3. Re-train demand forecast model
  4. Re-optimize next day with updated parameters
